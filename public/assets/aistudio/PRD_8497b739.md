# PRD — Sistem Digitalisasi Pembelajaran MPLB
**SMKS Ekonomika Depok · Jurusan Manajemen Perkantoran dan Layanan Bisnis (MPLB)**
Versi 1.0 · 27 Oktober 2026

> Dokumen ini adalah sumber kebenaran utama untuk AI agent yang membangun aplikasi. Baca bersama `ERD.md` (struktur data) dan `DESIGN.md` (tampilan). Bila ada konflik: PRD > ERD > DESIGN.

---

## 1. Ringkasan

Aplikasi web untuk mendigitalkan administrasi dan pembelajaran jurusan MPLB: data siswa, absensi, izin, tugas, surat berurutan, arsip digital, dan monitoring PKL. Tujuan utama adalah **menghilangkan pekerjaan manual** (Excel, kertas, rekap tangan).

### Tujuan
1. Semua data siswa, absensi, tugas, surat, dan PKL tersimpan di satu sistem.
2. Rekap bulanan dan semester dihasilkan otomatis dan bisa diekspor.
3. Seluruh aktivitas tercatat di log.
4. Nyaman dipakai di HP (siswa) dan laptop (guru, kepala program).

### Bukan tujuan (versi 1)
- Dipakai jurusan lain (hanya MPLB).
- Modul inventaris, perjalanan dinas, petty cash (fase 2).
- Aplikasi mobile native, notifikasi WhatsApp, absensi RFID/QR.

## 4. Kebutuhan Fungsional

Prioritas: **P0** wajib rilis pertama, **P1** penting, **P2** bila waktu cukup.

### 4.1 Autentikasi (P0)
- **FR-AUTH-1** Login siswa dengan NIS, guru dan kepala program dengan NIK, plus password.
- **FR-AUTH-2** Tombol "Masuk sebagai Tamu" membuat sesi role `guest` tanpa password.
- **FR-AUTH-3** Password di-hash (argon2 atau bcrypt). Password awal dibuat acak saat import dan **wajib diganti** pada login pertama (`must_change_password`).
- **FR-AUTH-4** Batasi percobaan login (misal 5 kali gagal, tunggu 15 menit).
- **FR-AUTH-5** Admin dapat reset password pengguna.
- **FR-AUTH-6** NIK tidak ditampilkan penuh di UI selain untuk admin.

### 4.2 Data Siswa (P0)
- **FR-SIS-1** Admin: tambah, ubah, hapus, lihat siswa dengan field NIS, NISN, nama, jenis kelamin, kelas, tingkat, HP, HP orang tua, foto, status (`aktif`, `lulus`, `pindah`, `keluar`).
- **FR-SIS-2** Pencarian (nama, NIS, NISN), filter (kelas, tingkat, status), pagination.
- **FR-SIS-3** **Hapus massal** dengan checkbox (pilih semua di halaman, pilih semua hasil filter). Memakai soft delete (`deleted_at`) dan dialog konfirmasi menampilkan jumlah data.
- **FR-SIS-4** Upload foto langsung ke storage, kompres di sisi klien, maksimum 2 MB.
- **FR-SIS-5** Guru melihat daftar siswa tanpa bisa mengubah. Siswa melihat profil sendiri. Guest melihat data tersamar (HP, NISN dimasking).

### 4.3 Data Guru (P0)
- **FR-GRU-1** Admin CRUD guru (NIK, nama, HP, foto, status aktif).
- **FR-GRU-2** Kepala program memiliki baris `guru` sekaligus akun role `admin`.

### 4.4 Import Excel (P0)
- **FR-IMP-1** Admin mengunduh template `.xlsx` untuk siswa dan guru.
- **FR-IMP-2** Upload file, sistem memvalidasi: kolom wajib, format, NIS/NISN/NIK unik, kelas valid.
- **FR-IMP-3** Tampilkan **preview**: jumlah baris valid dan error, dengan alasan per baris.
- **FR-IMP-4** Setelah konfirmasi, simpan **per batch** (100–200 baris per request) agar tidak terkena batas waktu serverless.
- **FR-IMP-5** Opsi saat data sudah ada: lewati atau perbarui.
- **FR-IMP-6** Hasil akhir: jumlah sukses/gagal dan unduhan laporan error (`.xlsx`). Setiap import tercatat di `import_log`.
- **FR-IMP-7** Akun login dibuat otomatis untuk setiap siswa/guru baru dengan password awal acak yang dapat diunduh admin sekali.

### 4.5 Kelas, Naik Kelas, Kelulusan (P0)
- **FR-KLS-1** Admin mengelola tahun ajaran dan kelas.
- **FR-KLS-2** Menu khusus **Naik Kelas**: pilih tahun ajaran asal dan tujuan, petakan kelas asal ke kelas tujuan, preview daftar siswa dengan checkbox (siswa tinggal kelas bisa dikecualikan), lalu konfirmasi.
- **FR-KLS-3** Aturan otomatis: tingkat 10 → 11, tingkat 11 → 12, tingkat 12 → status `lulus` dan `tahun_lulus` terisi.
- **FR-KLS-4** Seluruh proses dalam **satu transaksi database**. Gagal berarti rollback penuh.
- **FR-KLS-5** Setiap perubahan menulis `riwayat_kelas` dan satu baris `kenaikan_kelas_batch`.

### 4.6 Absensi (P0)
- **FR-ABS-1** Guru membuat sesi absensi (kelas, mapel, tanggal, jam ke) lalu menandai status per siswa.
- **FR-ABS-2** Status yang valid: `hadir`, `sakit`, `izin`, `alpha`, `terlambat`, `dispensasi`.
- **FR-ABS-3** Tombol "Semua Hadir" lalu ubah yang berbeda saja. Tampilan HP berupa kartu dengan tombol status besar.
- **FR-ABS-4** Satu siswa hanya punya satu status per sesi (unik).
- **FR-ABS-5** Siswa melihat riwayat dan persentase kehadiran sendiri.

### 4.7 Izin dengan Bukti Foto (P0)
- **FR-IZN-1** Siswa mengajukan izin (jenis: sakit, izin, dispensasi; tanggal mulai dan selesai; alasan) dengan **foto bukti wajib**.
- **FR-IZN-2** Upload dari kamera atau galeri, langsung ke storage.
- **FR-IZN-3** Guru atau admin menyetujui atau menolak dengan catatan.
- **FR-IZN-4** Izin yang disetujui otomatis menulis status ke absensi pada tanggal terkait.

### 4.8 Tugas Pembelajaran (P0)
- **FR-TGS-1** Guru membuat tugas (judul, deskripsi, lampiran, kelas, mapel, deadline).
- **FR-TGS-2** Siswa mengumpulkan jawaban berupa file dan/atau teks. Setelah deadline ditandai `terlambat`.
- **FR-TGS-3** Guru memberi nilai dan umpan balik. Siswa melihat nilai sendiri.
- **FR-TGS-4** Export hasil tugas dan nilai per kelas ke Excel.

### 4.9 Surat Berurutan dan Arsip Digital (P0)
- **FR-SRT-1** Admin mengelola **jenis surat**, masing-masing dengan **kode berbeda** (contoh: SK, SD, SP).
- **FR-SRT-2** Siswa membuat surat (pilih jenis, isi, lampiran opsional), status awal `draft`, lalu `diajukan`.
- **FR-SRT-3** **Guru yang memverifikasi**: hasilnya `revisi` (wajib catatan) atau `valid`.
- **FR-SRT-4** Siswa memperbaiki surat berstatus `revisi` lalu mengajukan ulang.
- **FR-SRT-5** **Nomor surat diterbitkan hanya saat status menjadi `valid`**, berurutan per jenis surat per tahun, format `{nomor 3 digit}/{kode}/MPLB/{bulan romawi}/{tahun}`, contoh `007/SK/MPLB/X/2026`.
- **FR-SRT-6** Penomoran memakai tabel counter yang dikunci dalam transaksi. **Tidak boleh ada nomor kembar atau nomor loncat** karena race condition.
- **FR-SRT-7** Surat valid otomatis masuk **Arsip Digital** dan dapat dicari berdasarkan nomor, jenis, tanggal, dan pembuat.
- **FR-SRT-8** Export surat valid ke PDF.

### 4.10 PKL (P0)
- **FR-PKL-1** Input data tempat PKL (DUDI): nama, alamat, kontak, pembimbing industri.
- **FR-PKL-2** Penempatan siswa: DUDI, **divisi**, tanggal mulai, tanggal selesai, durasi, guru pembimbing, dan **catatan**. Siswa satu perusahaan tetapi beda divisi dibedakan lewat kolom divisi dan catatan.
- **FR-PKL-3** Satu perusahaan menampilkan daftar siswa yang ditempatkan di sana beserta divisinya.
- **FR-PKL-4** **Jurnal harian** diisi siswa hanya untuk **tanggal hari ini** (dicek di server pakai zona waktu Asia/Jakarta). Tidak boleh mengisi atau mengubah tanggal lain.
- **FR-PKL-5** Guru memantau dan memverifikasi jurnal (`valid` atau `revisi` dengan catatan).
- **FR-PKL-6** Export rekap jurnal per siswa dan rekap per DUDI.

### 4.11 Rekap dan Export (P0)
- **FR-REK-1** Rekap absensi **per bulan** dan **per semester**, per kelas dan per siswa, dengan jumlah tiap status dan persentase kehadiran.
- **FR-REK-2** Rekap dihitung dengan query agregasi dari tabel `absensi` (tidak disimpan terpisah).
- **FR-REK-3** Export ke Excel dan PDF: rekap absensi, data siswa, nilai tugas, jurnal PKL, daftar surat.
- **FR-REK-4** Rekap kegiatan mencakup tugas dan PKL dalam periode yang sama.

### 4.12 Log Aktivitas (P0)
- **FR-LOG-1** Setiap aksi tercatat: login, create, update, delete, import, export, approve, reject, naik_kelas.
- **FR-LOG-2** Simpan user, role, aksi, entitas, id entitas, data sebelum/sesudah (JSON), IP, user agent, waktu.
- **FR-LOG-3** Halaman log hanya untuk admin dengan filter pengguna, aksi, dan tanggal. Log tidak bisa diubah atau dihapus lewat UI.

### 4.13 Dashboard (P1)
- Admin: jumlah siswa aktif, kehadiran hari ini, izin menunggu, surat menunggu verifikasi, penempatan PKL.
- Guru: sesi hari ini, izin dan surat menunggu, tugas belum dinilai.
- Siswa: kehadiran saya, tugas mendekati deadline, status surat, jurnal PKL hari ini.
- Guest: ringkasan umum tanpa data pribadi.

## 5. Kebutuhan Non-Fungsional

| Area | Persyaratan |
|---|---|
| Platform | Web responsif, mobile-first. Layar minimum 360 px |
| Hosting | Vercel |
| Performa | Halaman utama dimuat < 3 detik di 4G. Tabel memakai pagination sisi server |
| Keamanan | HTTPS, hash password, validasi semua input di server (zod), proteksi CSRF, batasi tipe dan ukuran upload |
| Privasi | NIK, NISN, HP disamarkan untuk guest dan peran yang tidak berhak |
| Integritas | Transaksi untuk naik kelas dan penomoran surat. Soft delete untuk data siswa |
| Zona waktu | Asia/Jakarta untuk semua aturan "hari H" |
| Bahasa | Antarmuka Bahasa Indonesia |
| Aksesibilitas | Kontras warna minimal WCAG AA, target sentuh minimal 44 px, status tidak hanya dibedakan warna |
| Upload | Foto maks 2 MB (setelah kompres), dokumen maks 10 MB, upload langsung dari browser ke storage |

## 6. Arsitektur dan Tech Stack

| Lapisan | Pilihan |
|---|---|
| Framework | Next.js (App Router) + TypeScript |
| UI | Tailwind CSS + shadcn/ui |
| Auth | Auth.js (Credentials), sesi JWT |
| ORM | Prisma |
| Database | PostgreSQL (Neon, Supabase, atau Vercel Postgres) |
| Storage | Vercel Blob atau Supabase Storage |
| Excel | SheetJS (baca), ExcelJS (tulis) |
| PDF | `@react-pdf/renderer` |
| Validasi | zod |

Struktur folder:

```
src/
├─ app/
│  ├─ (auth)/login
│  ├─ (app)/ dashboard, siswa, guru, kelas, naik-kelas, absensi, izin,
│  │         rekap, tugas, surat, arsip, pkl, jurnal-pkl, import, log, pengaturan
│  └─ api/ (upload, export)
├─ lib/ (auth, rbac, db, excel, pdf, logger, penomoran)
├─ components/ (ui, tables, forms, layout)
└─ prisma/schema.prisma
```

Catatan teknis wajib:
1. Middleware memeriksa sesi dan role. Server action memeriksa ulang role.
2. Fungsi serverless Vercel dibatasi ukuran request, jadi **file diupload langsung dari klien ke storage**.
3. Import dan hapus massal dipecah per batch.

## 7. Aturan Bisnis Ringkas

1. Guest tidak pernah menulis ke database.
2. Siswa hanya melihat dan mengubah data miliknya sendiri.
3. Izin wajib punya foto bukti.
4. Jurnal PKL hanya bisa diisi pada hari H.
5. Nomor surat hanya terbit saat surat `valid`, berurutan per jenis per tahun.
6. Kelulusan mengubah status siswa menjadi `lulus`, tidak menghapus data.
7. Menghapus siswa adalah soft delete. Hapus permanen hanya admin dengan konfirmasi ketik.
8. Setiap aksi tulis tercatat di log.

## 8. Kriteria Penerimaan (contoh utama)

| ID | Skenario | Hasil yang diharapkan |
|---|---|---|
| AC-1 | Guest mencoba menambah siswa lewat UI atau API | Ditolak 403, database tidak berubah |
| AC-2 | Admin import 300 siswa dengan 5 baris NIS duplikat | 295 tersimpan, 5 masuk laporan error, tercatat di `import_log` |
| AC-3 | Admin menjalankan naik kelas untuk 3 kelas | Tingkat 10→11, 11→12, 12→`lulus`; gagal di tengah berarti tidak ada perubahan |
| AC-4 | Dua guru memverifikasi surat jenis SK bersamaan | Nomor berurutan, tidak kembar, tidak loncat |
| AC-5 | Siswa mengisi jurnal PKL untuk kemarin | Ditolak dengan pesan jelas |
| AC-6 | Siswa mengajukan izin tanpa foto | Form tidak bisa dikirim |
| AC-7 | Guru menyetujui izin 3 hari | Absensi 3 hari terisi otomatis sesuai jenis izin |
| AC-8 | Admin export rekap semester | File Excel berisi jumlah tiap status dan persentase per siswa |
| AC-9 | Admin memilih 20 siswa lalu hapus massal | Dialog konfirmasi menampilkan jumlah, data ter-soft-delete, log tercatat |
| AC-10 | Layar 360 px | Tidak ada scroll horizontal, tabel berubah menjadi kartu |

## 10. Asumsi (konfirmasi ke Kepala Program)

1. Absensi diinput per sesi pelajaran oleh guru.
2. Satu siswa memiliki satu penempatan PKL per tahun ajaran.
3. Siswa boleh membuat semua jenis surat, guru mana pun boleh memverifikasi.
4. Hanya satu sekolah dan satu jurusan (tidak multi-tenant).
5. Kode jenis surat ditentukan admin, bukan hardcode.
